# vllm-serve-bench

A production-style LLM inference service on vLLM, with a Go load generator and telemetry harness
built to answer one question honestly: **how much useful output can this GPU produce while still
meeting a latency objective, and which knob moves that number?**

It serves `Qwen/Qwen2.5-7B-Instruct` with `vllm/vllm-openai:v0.29.0` (pinned by digest) on one RTX
5090. It measures a baseline, chooses SLOs from that baseline, and then runs three experiments
written up as Baseline → Hypothesis → Change → Benchmark → Result → Trade-off. It is a take-home
exercise, time-boxed to 4–6 hours of build time.

What each experiment showed:

- **A: a larger scheduler token budget** (`--max-num-batched-tokens` 2048 → 8192). Long prompts
  are admitted faster, so throughput-profile TTFT falls. But neither SLO boundary moves, and the
  larger budget costs KV pool capacity. The default stays.
- **B1: prefix caching off.** It removes most of the interactive profile's goodput, and the loss
  *grows* with load, which refutes the prediction that it would fade into queueing. Recomputing a
  shared prefix competes with decode. The profile without a shared prefix is unaffected.
- **B2: an FP8 checkpoint produced here** with llm-compressor
  ([published](https://huggingface.co/wrbooth/Qwen2.5-7B-Instruct-FP8-Dynamic)). It gives the
  largest gains on both profiles: faster decode and a larger KV pool. On a small fixed check set
  its answers match bf16 on every exact-answer item. The prediction that it would move the
  throughput SLO boundary was wrong.

## How the numbers are kept honest

- **The SLO was chosen after the baseline**, from where the baseline degrades, with the reasoning
  and rejected alternatives written down in [wiki/log.md](wiki/log.md). It is stored in
  [docs/slo.json](docs/slo.json).
- **The recorded argv is what the engine actually ran:** PID 1's argv inside the container, not the
  compose file (vLLM keeps the last of a repeated flag). The KV pool size and host facts come from
  the running engine.
- **No run is served from a warm cache:** `bench run` empties vLLM's prefix cache before every
  level, prompts are unique within a run, and a telemetry check flags any level whose requests
  prefilled less than their unique part. That check caught a real contamination bug, and the fix
  is in the history, not hidden.
- **The harness is cross-checked** against `vllm bench serve` on the same workload
  ([results/verify/](results/verify/), generated by `bench verify`).
- **Prompts are generated from a seed** out of a single-token word list, so every request's prompt
  length is known in advance and checked against the server's `prompt_tokens`.
- **Raw results are committed and never edited.** A bad run is superseded, not rewritten, and the
  supersession is logged.
- **Hypotheses were committed before the data**, and predictions that failed are reported as
  failed.

## Reproduce

On a host with an NVIDIA GPU, Docker with CDI (or the NVIDIA runtime), and the model in the
Hugging Face cache. The scripts expect a deploy directory with `bin/`, `compose/` and `scripts/`
side by side, which is how the GPU host was laid out:

```sh
GOOS=linux GOARCH=amd64 make build          # bin/bench (or use ghcr.io/wrbooth/vllm-serve-bench)
mkdir -p ~/vsb && cp -r bin scripts ~/vsb/ && cp -r deploy/compose ~/vsb/compose
cd ~/vsb/compose
printf 'HF_CACHE=%s\nMODELS_DIR=%s\n' ~/.cache/huggingface ~/vsb/models > .env.local

./engine.sh up baseline Qwen/Qwen2.5-7B-Instruct   # pinned image; waits for readiness; prints the real argv
../scripts/sweep.sh baseline ../results/baseline   # both profiles, cache reset before every level
```

Then, back in the repo, with the run directories copied into `results/`:

```sh
bin/bench report --out docs/03-results.md results/<run-dir> ...
```

- **Start warm:** start the engine twice after changing its flags. The compile cache affects the
  KV pool size ([wiki/gpu-host.md](wiki/gpu-host.md)).
- **Cross-check:** [scripts/cross-check.sh](scripts/cross-check.sh), then `bench verify`.
- **Quantize and quality-check the FP8 checkpoint:** [scripts/quantize/](scripts/quantize/).
- **Kubernetes:** the manifests in [deploy/k8s/](deploy/k8s/) are validated in CI but have not been
  applied to a cluster.

## Limitations

- **One consumer GPU:** no NVLink, no DCGM profiling counters, no tensor parallelism. Anything about
  those in the architecture doc is design, not result.
- **One run per configuration:** a repeat of the baseline agreed closely, but differences of a
  couple of percent are within noise.
- **Closed-loop load:** it understates tail latency under open arrival.
- **The FP8 quality check is a smoke test**, not an evaluation.
