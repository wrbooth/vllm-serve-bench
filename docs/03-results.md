# Results

Every figure on this page is generated by `bench report` from a committed
run directory under [`results/`](../results/) and the committed SLO file
[`docs/slo.json`](slo.json). Generated text sits between
`bench-report:begin` and `bench-report:end` markers, and the first line of
each block records the exact command and the inputs it was made from. The
command rewrites only what is between the markers; the prose outside them is
hand-written and contains no measured numbers. Metric definitions,
percentile method and the goodput definitions are in
[02-architecture.md](02-architecture.md#metric-definitions-client-side-per-request).

## How to read the tables

- **c** is the closed-loop concurrency: that many requests in flight for the
  whole measured window, after a warmup that is excluded.
- **SLO cells** show the level's percentile and its margin against the
  limit, so a pass or a fail by a hair is visible as such. A value equal to
  the limit passes.
- **Max compliant goodput** (the headline) is the highest output tok/s
  among the levels that meet the SLO, have no errors, and pass the engine
  check. It answers "how much can this engine serve while every level's
  tail stays inside the budget".
- **Per-request goodput** counts only the output tokens of requests that
  met every limit on their own. It shows how much of a failing level's
  output was still useful, and it is never the headline.
- **Engine check**: the engine-side guard from the cross-check. A level
  whose prompts were served from the prefix cache instead of prefilled is
  marked `CACHED` and does not count.

The SLO was chosen after the baseline sweeps, from their data, and the
reasoning is recorded in the [wiki log](../wiki/log.md) (the two SLO
decision entries). In short:

- **Interactive** is judged on what a chat user feels: time to the first
  token, and the pace of the tokens after it. Both limits are user-facing
  budgets (a first token that reads as instant, and a token rate well above
  reading speed), not values fitted to the curve. They happen to fall on
  the baseline's knee, which leaves every experiment room to move the
  headline. A looser pair would have put the boundary between two levels
  with the same throughput, where no experiment could show a gain; a p99
  pair would rest on too few samples per level.
- **Throughput** is judged on completion time, because a batch
  summarisation user waits for the finished summary. TTFT and TPOT stay in
  the tables as diagnostics. A TTFT-plus-TPOT alternative put its boundary
  on a knife edge at a level with no throughput advantage.
- **Known weakness.** The first interactive level that fails the SLO fails
  its TPOT bound by only a few percent (the margin is in the headline table
  below). A small TPOT improvement would bring that level inside and move
  the headline by a large step, which would overstate a small effect. That
  is why every SLO cell carries its margin, and why each experiment's
  write-up quotes the margin, not only the pass or fail.

## Experiment A: scheduler budgets (batching)

- **Baseline:** the tables above, at `--max-num-batched-tokens 2048` (vLLM's default on this card).
- **Hypothesis** (logged before the data, [wiki/log.md](../wiki/log.md)): at 2048 each engine step
  fits about one throughput-profile document beside the running decodes, so long prompts are
  admitted slowly and every decode step carries a large prefill chunk. A larger budget should
  admit documents faster, shrink the throughput dip past the peak, raise output tok/s from the
  peak upward, and raise TPOT (steps carrying more prefill take longer). The interactive
  profile's prefills are short, so it is the control: no material change expected.
- **Change:** `--max-num-batched-tokens 8192` (`deploy/compose/engine/a-mnbt8192.env`), the value
  vLLM itself uses on cards of 70 GB and up. Nothing else changes. The engine was started twice
  so the measured start had a warm compile cache.
- **Benchmark:** the levels around each baseline knee, same seed, prefix cache reset before every
  level (`scripts/sweep.sh` with `LEVELS_<PROFILE>`).
- **Result:** partly supported, and neither SLO boundary moves.
  - Throughput TTFT falls at the middle and upper levels: long prompts really are admitted
    faster. Output tok/s rises modestly past the peak.
  - The dip past the peak survives, smaller. So the prefill budget is only part of its cause.
  - TPOT did not rise as predicted.
  - The interactive control moves by amounts one run per config cannot separate from noise.
  - Max compliant goodput is essentially unchanged on both profiles: the first failing level
    still fails.
- **Trade-off:** the larger step budget reserves more activation memory, so the KV pool is
  smaller (engine facts below). At the top throughput level that shows up as more preemption and
  worse queueing TTFT. For this card and these SLOs the default budget stays.

## Experiment B1: prefix caching off

- **Baseline:** the tables above, with prefix caching on (vLLM's V1 default). The interactive
  profile's ~300-token system prompt is shared by every request, so after the first request each
  new one prefills only its ~100-token unique turn plus template.
- **Hypothesis** (written in [02-architecture.md](02-architecture.md#experiments) before any data):
  with caching off, every request prefills its whole prompt. So TTFT rises by roughly the shared
  fraction at low concurrency, the gap shrinks at high concurrency where TTFT is dominated by
  queueing, and the throughput profile, which has no shared prefix, is unaffected.
- **Change:** `--no-enable-prefix-caching` (`deploy/compose/engine/no-prefix-cache.env`), an
  ablation of a default. Nothing else changes, and the KV pool is the same size.
- **Benchmark:** the interactive profile over its full sweep, and throughput at the two levels
  around its knee, as a check on "unaffected". A first interactive run covered only the knee levels.
  It could not locate the SLO boundary, which lies below them, so the full run supersedes it. Both
  are committed (`results/b1-no-prefix-cache/`).
- **Result:** partly refuted, and informatively so.
  - **Low concurrency:** TTFT rises as predicted.
  - **High concurrency:** the gap does not shrink, it grows. Interactive throughput falls well
    below the baseline from the middle of the sweep up, and TPOT rises with it. Recomputing the
    shared prefix for every request is real GPU work that competes with decode under the same
    per-step budget, so it costs throughput and per-token latency, not only queueing time.
  - **SLO:** the SLO boundary moves down to a much lower concurrency, and max compliant goodput
    drops accordingly (headline and comparison tables).
  - **Throughput profile:** barely moves, as predicted.
- **Trade-off:** what the default buys. Prefix caching costs nothing measurable here (the same KV
  pool size, and no throughput penalty on the profile without a shared prefix), and on a shared
  prompt it is worth a large share of the achievable goodput. The engine check reads a
  caching-off engine correctly: with no cache lookups at all, it counts every prompt token as
  prefilled.

## Experiment B2: self-made FP8 checkpoint

- **Baseline:** the tables above: bf16 weights, the same engine flags.
- **Hypothesis** (logged before serving it, [wiki/log.md](../wiki/log.md)): decode is
  bandwidth-bound at low concurrency, so halving the weight bytes should cut TPOT there, by less
  than half. The KV pool should grow, pushing the throughput knee right. FP8 GEMMs should raise
  interactive tok/s where the baseline was compute- or power-bound, and may bring the next level
  inside the SLO. Quality is checked separately.
- **Change:** a checkpoint produced here, not a download. [scripts/quantize/quantize.py](../scripts/quantize/quantize.py)
  applies llm-compressor's `FP8_DYNAMIC` scheme: FP8 weights with one static scale per output
  channel, FP8 activations with a scale per token computed at run time (so no calibration data),
  `lm_head` left in bf16, and the KV cache unquantized. It is served with exactly the baseline
  flags (`engine/b2-fp8.env`). vLLM selects a CUTLASS FP8 kernel for it. The checkpoint's
  `provenance.json` records the source snapshot and tool versions.
- **Benchmark:** the baseline knees plus interactive c=1 (the bandwidth-bound case), same seed,
  prefix cache reset before every level. The warm KV pool is in the engine facts below.
- **Result:** mostly supported; one prediction refuted.
  - TPOT falls at almost every level. At c=1, the bandwidth-bound case, it falls by less than
    half, as predicted.
  - The KV pool is much larger, and throughput rises across both sweeps.
  - **Interactive:** the first level that failed the SLO in the baseline now passes with real
    margin on both bounds, not by a hair. So max compliant goodput moves up a concurrency level.
  - **Throughput:** the SLO boundary does _not_ move. The next level up still misses E2E p95 by
    a wide margin, so the prediction that it might come inside was wrong. Max compliant goodput
    still rises substantially, at the same level, because every request finishes sooner.
  - Queueing at the top throughput levels mostly disappears (TTFT), because the larger pool
    admits more sequences.
- **Quality** ([results/quality/report.md](../results/quality/report.md), generated by
  `quality.py compare`): on a fixed set of exact-answer and open prompts, run greedily, the FP8
  model answered exactly the same exact-answer items correctly as bf16. Its misses were the same
  two items, wrong the same way. Most replies were identical to the byte. This is a
  smoke-level check on a small hand-written set, scored by containment, not an eval. A real
  rollout would gate on an eval suite; published FP8 results for this model family are the
  outside reference.
- **Trade-off:** at the top throughput level the larger pool admits more concurrent sequences,
  and each step shares the GPU between more of them, so TPOT p95 there gets _worse_ than the
  baseline even as TTFT and E2E improve. Separately, weights stored in 8 bits carry some quantization error. That shows up here as
  some open-ended replies drifting from the bf16 wording after a shared prefix, with no loss on
  the exact-answer items. Producing the checkpoint costs a pinned toolchain and a minute of GPU,
  and it must be re-made (and re-checked) for every new base model or tool version.
